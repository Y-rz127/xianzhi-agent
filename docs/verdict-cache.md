# 命盘裁决缓存与「毫秒级出盘」

> 适用代码：`app/agent/verdict.py`、`app/domain/chart_builder.py`、`app/api/xianzhi_chart.py`、
> `app/api/xianzhi_kline.py`、`app/tools/cache.py`、`app/db/schema.py`
>
> 本文回答三个问题：**命盘的身份是什么**、**一次请求里哪些环节能省**、**哪些东西绝对不能跨人共享**。

---

## 一、两种内容、两把钥匙

同一张盘在一次请求里其实产生两类东西，它们的"身份"（缓存键）**刻意不同**：

| | 结论类（裁决） | 派生类（命盘 payload / K 线） |
|---|---|---|
| 内容 | 强弱档位、格局、用神、五神、`useful_hint` | 四柱详情、神煞、大运/流年表、细盘、K 线蜡烛与评分 |
| 身份 | **四柱 + 性别** | **精确出生时刻 + 经度 + sect/yun_sect** |
| 凭什么 | 裁决的每一项输入都是四柱的函数 | 起运岁数由"出生时刻到节气的距离"决定，同四柱也可能不同 |
| 共享范围 | **跨人**（同盘同判） | **仅本人这张盘**（不跨人） |
| 存储 | PG `chart_verdicts`（跨进程/跨副本） | 进程内 LRU `bazi_cache`（每副本各自预热）+ `session_birth_info.chart_json` 快照 |

### 裁决指纹

```python
verdict_key = sha256(f"pillars:{四柱}|{性别}")[:16]     # 例：甲申庚午壬申甲辰|男 → 13d9767b7a10df24
```

`pillars:` 前缀让键空间与"出生时刻"那套明确分开，排查时不会看混。命中条件还要**加上两个版本号**：

```
verdict_key == ?  AND  engine_version == 当前  AND  prompt_version == 当前  AND  status = 'ok'
```

引擎或提示词一 bump，旧行就取不到 —— 用 `scripts/prune_verdicts.py --apply` 清理（见该脚本 docstring）。

### 出生时刻指纹（另一把钥匙）

```python
birth_key = sha256(f"{chart.birth.solar}|{性别}")[:16]   # 注意是**真太阳时校正后**的时间
```

它服务于：命盘画像/断事（`chart_profiles`/`chart_facts` 按人）、以及本改造之前写入的裁决行的兜底。
读侧必须复算同一套「标准化 → 校正」（`verdict.chart_hash_for_input`），否则会和写侧错位 —— 见文末事故记录。

## 二、三条入口的时序

三个入口都遵循同一条主线：**先算四柱 → 查指纹 → 命中就回放 → 没命中才判**。

### 1. 面板「保存并排盘」`POST /chart/save`

```
校验/标准化 birth_time → 经度解析（显式经度 > 地名匹配 > 0=不校正）
  → 排计算版（引擎）
  → 落库出生信息 session_birth_info（失败 → 503，不假装保存成功）
  → 应用已落库裁决（命中则毫秒级，status=verdict）
  → 落命盘快照 chart_json（status=pending|stale|verdict）+ 预热计算版 payload 缓存
  → 立刻返回计算版（verdict_status 告诉前端"终审生成中"）
  → 后台补判 → 回调：快照覆盖成终审版 + 预热终审版 payload 缓存
```

### 2. 详情页/K 线 `GET /chart`、`GET /kline`

```
排盘前：算四柱指纹（0.1ms）→ verdict_cache_namespace 判定 v/s/p
  v → 直接回放当前版本裁决
  s → 旧版裁决先顶上（标注"旧版"），后台重判
  p → 计算版先出，后台补判
  → 完整排盘 → 应用裁决 → 格式化 payload → 进程内 LRU 缓存（key 含 v/s/p 命名空间）
```

### 3. 聊天挂盘（正则/工具提取 ⇒ `set_chart_context`）

```
挂盘即落 session_birth_info；终审走 chart_with_verdict_sync：
命中缓存毫秒应用，否则派后台，绝不阻塞对话
```

## 三、实测耗时（本机，不含 LLM）

| 环节 | 耗时 |
|---|---|
| 只算四柱（算指纹） | 0.1–0.5 ms |
| 查裁决（PG 索引命中） | ~5.7 ms |
| 完整排盘（大运 12 + 流年 5） | 23–80 ms（冷热差异） |
| 格式化 payload（含细盘 xipan） | ~3 ms |
| **首次响应（进程缓存未命中）** | **≈ 33–90 ms** |
| **再次/下拉刷新（LRU 命中）** | **~0.1 ms 级** |

所以口径要说准：**命中裁决省掉的是 LLM（秒级 → 0）**；排盘本身照跑。第一次看某张盘是"几十毫秒且不等 LLM"，
再次才是真正的毫秒级。

## 四、边界（改这块代码前必读）

1. **不要把派生缓存也换成四柱键。** 四柱相同不保证起运岁数相同 ⇒ 大运年份可能差一年。
   `chart_api` / `kline_api` 的缓存键必须保留精确时刻 + 经度。已有测试钉住（`tests/test_verdict_keys.py`）。
2. **画像/断事不能跨人。** `chart_profiles(user_id, chart_hash)`、`chart_facts` 是"某个人的盘"，
   沿用出生时刻口径；把四柱键用过去会让 A 的断事喂给同四柱的 B。
3. **版本门槛不可省。** 只按指纹命中不看版本，等于把旧口径结论永远钉在盘上。
4. **`invalid`/`failed` 不写 alias、不做"已判"缓存**，否则一次上游抖动会永久钉住失败。
5. **指纹不含 `yun_sect`**（只影响起运/大运年份），但**含 `sect`**（晚子时换日会改日柱）。

## 五、事故记录（为什么会有这篇文章）

**2026-10-24**：详情页一直显示「终审版生成中」，且同一张盘反复重判（`chart_verdicts` 里
`2004-06-22` 出现 08:00 / 08:05 / 08:50 / 07:28 多行）。

根因两处叠加：
- 裁决指纹当时是"出生时刻"，且**读侧用查询串原始时间**、**写侧用真太阳时校正后的时间**
  （08:15 + 108.63° 校正为 07:28）→ `2f629bf2…` vs `c621b85b…`，永远 miss；
- 命名空间恒为 `p`，命中的是先前缓存的计算版 payload，连"构建后应用终审"的机会都没有。

修复顺序：`fca46bd` 先把两侧指纹对齐（`chart_hash_for_input`），`e3d9c01` 再把裁决身份整体换成
四柱指纹（跨人复用，从根上消除"输入侧写法差异"这类错位），`ab007a2` 清理了 104 行取不到的旧裁决。

教训：**缓存键要建在"业务的真实身份"上**。裁决只认四柱，就不该拿时刻当它的键 —— 否则每一次
"换个写法/换个地点/开关一下出生地"都会变成一次 miss 和一次 LLM 计费。
