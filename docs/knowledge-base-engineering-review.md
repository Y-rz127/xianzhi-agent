## 二、高：`00_知识库总索引.md` 已与其所描述的事实脱节

索引自称服务于「RAG 检索路由、Worker 调用、知识库维护参考」（`00_知识库总索引.md:3`），但已失去作为权威清单的资格。

### H1. `35_身材样貌断法.md` 未被索引引用

索引对 01–34、古籍01–12 逐条列表，**唯独没有 `35_身材样貌断法.md`**。而该文档：

- 是**第 3 大文档**（25.3 KB / 25 chunks / 占全部片段 3.2%，仅次于 07 和 27）；
- 有专门的测试（`test_knowledge_docs.py:1238-1268`，含 `木瘦金方水主肥`、`神相全编`、`伪造古籍`、`医疗诊断` 等断言）。

即：内容与测试都在，**只有索引漏了**。对于一份声明用于检索路由的清单，这是功能性缺口。

### H2. 索引自身作为可检索正文进入知识库

`infer_doc_type()` 按文件名推断类型（`knowledge.py:37-54`），`00_知识库总索引.md` 不含任何 `_RULE_KEYWORDS`（`断法/规则卡/格局/官非/性格/贫富/男女命/流月流日`），因此落到兜底分支：

```python
return "theory"          # knowledge.py:54  → 权重 1.00（DOC_TYPE_WEIGHT["theory"]）
```

实测该文档产出 **12 个 chunk**，`doc_type=theory`，权重与真正的理论正文相同。其内容形如：

```
[知识库总索引｜八字命理知识库总索引]
> 本文档为八字命理预测智能体（Xianzhi-Agent）知识库的总目录，含全部文档的定位…
> **文档总数**：47 份（基础理论 9 + 断法规则 26 + 古籍 12）
```

即目录页会以与正文**同等权重**参与检索，并有 12 次机会被注入模型。目录页的信息量对断事毫无价值，却挤占了 `max_docs` 名额。

### H3. 计数错误：声称 47，实为 48

- `00_知识库总索引.md:6`：「文档总数：**47 份**（基础理论 9 + 断法规则 26 + 古籍 12）」
- 实际 48 篇内容文档（9 + 27 + 12 = 48）。断法规则层少计 1 篇，差额正是 H1 漏掉的 35。

三项数字中 `9 + 26 + 12 = 47` 内部自洽，说明是**编制时的遗漏**，而非笔误。

### H4. 与源码注释冲突：`10b` 编号解释

索引 `:34` 将 `10b` 列为正式编号，`00:156` 有「10b编号说明」；但 `knowledge.py:42` 的注释写「序号 ≥10 的实战断事文档…」。代码注释与索引对编号体系的理解并不一致（不构成运行缺陷，属注释失准）。

### 修复建议

1. 在索引 §2.1 补入 `35 | 身材样貌断法 | 五行形相、十神泄秀、高矮胖瘦、神煞形貌 | …`，并把 `:6` 的 47 改为 48（或改为「48 份」并同时修正三个分项）。
2. **把索引排除出检索语料**，二选一：
   - 在 `load_knowledge_docs()` 中跳过 `00_`，或
   - 在 `DOC_TYPE_WEIGHT` 增加 `"index": 0.0` 并在 `infer_doc_type()` 中优先识别 `00_`/`总索引`。
   前者更彻底：索引是给人读的维护件，不是断事依据。
3. 增加回归守卫，把 H1/H3 变成机拦：

```python
def test_index_references_every_doc():
    """索引必须覆盖每篇内容文档，且计数与文件数一致。"""
    docs = sorted(p.name for p in KNOWLEDGE_DIR.glob("*.md") if p.name != "00_知识库总索引.md")
    index = (KNOWLEDGE_DIR / "00_知识库总索引.md").read_text(encoding="utf-8")
    missing = [d for d in docs if d[:-3].split("_", 1)[1][:6] not in index]
    assert not missing, f"索引未收录: {missing}"
    assert f"{len(docs)} 份" in index, f"索引计数应为 {len(docs)}"
```

这条守卫能同时防住 H1 与 H3，且实现成本很低——建议优先做。

### M1. 真太阳时：文档要求「经度修正 + 均时差」，代码只做经度修正

> 同时纠正了原实现经度项方向写反的问题；`chart_builder`、合婚工具、聊天挂盘共用同一实现。

知识库三处声明（`00_知识库总索引.md:118`、`08_八字排盘基础.md:3`、`24_标准分析流程.md`）真太阳时校正包含**均时差**。修复前代码实现为：

```python
# chart_builder.py:332-337（修复前）
solar_correction_min = round((120 - longitude) * 4)   # 仅经度差 × 4 分钟，且方向与公式相反
```

### M2. 夜子时口径：运行时正确，但依赖第三方库默认值；且文档要求"必须提示"未被保证

这是本次审查中最值得关注的一项，因为它是系统**旗舰口径**。

**文档侧**四处完全一致，且措辞是"本系统固定口径"：

- `00_知识库总索引.md:116`：「夜子时：**日柱沿用当日，时干按次日五鼠遁取时干**（分支B）」
- `08_八字排盘基础.md:130`：「**AI 排盘默认采用早子时派 + 分支 B**…并在界面/接口输出中标注所采用流派」
- `24_标准分析流程.md:44`：「**统一口径**：本系统采用"夜子时仍属当日"口径」
- `24_标准分析流程.md:46`：「**遇到 23:00-23:59 出生用户，必须主动提示时辰存在排盘分歧风险**」

**代码侧**：

```python
# chart_builder.py:345-346
if sect != 2:
    ec.setSect(sect)
```

默认路径（`sect=2`）**根本不调用 `setSect`**，行为完全继承 lunar-python 的内部默认值。实测（1990-05-20 23:30）：

| 取值方式 | 四柱 |
|---|---|
| 库默认（不调用 setSect） | 庚午 辛巳 **乙酉** 戊子 |
| `setSect(1)` | 庚午 辛巳 **丙戌** 戊子 |
| `setSect(2)` | 庚午 辛巳 **乙酉** 戊子 |

而 `EightChar.__init__` 中 `self.__sect = 2`。

**结论（两段，需分开看）**：

1. **当前行为是正确的** —— 日柱=乙酉（沿用当日）、时干=戊（按次日日干起五鼠遁），与文档声明**逐字相符**。这一点必须讲清楚，不是 bug。
2. **但正确性是隐式的**：代码从未表达"我要 sect=2"这一意图，只是恰好等于第三方库的内部默认值。一旦 lunar-python 调整默认值（或升级引入行为变更），旗舰口径会**静默失效**，且没有任何测试或断言会报警。

**附带问题（同源、更具体）**：`sect` 参数在不同工具间语义互相矛盾，且部分工具根本没接：

- `bazi.py:152` / `:179` / `:490`：「1=按日期精确，2=按日期精确2（默认）」
- `bazi.py:371`（合婚）：「1=早子时（子时换日），2=晚子时（默认，子正换日）」
- `xianzhi_kline.py:190`：「1=晚子时日柱算当天，2=次日」

同名的 `1` 在三处分别意味着"早子时换日""按日期精确""晚子时日柱算当天"，其中 `bazi.py:371` 与 `xianzhi_kline.py:190` 对 `1` 的描述**相反**，而两者对 `2` 的描述也不自洽。此外 `bazi_liunian`(`:234`)、`bazi_analysis`(`:172`)、`bazi_dayun`(`:204`) 等以硬编码 `2` 调 `build_bazi_chart`（如 `:219`、`:253`），调用方传入的 `sect` 被丢弃。

**关于"必须主动提示"**（此处需精确，勿夸大）：`chart_builder.py:428-429` 在 `h == 23 or h == 0` 时产生 warning，且该 warning **确实会到达模型**——两条路径都确认：

- `workflow_messages.py:494`：`"口径: " + "；".join(chart.warnings)`（Workflow 事实块）
- `chart_format.py:59-60`：`if chart.warnings: lines += ["", "【校验提示】"] + …`（排盘文本）

因此**交付是可靠的**。真正的落差在于**强度与形式**：它是一条陈述性文字（"建议保留早晚子时口径"），混在事实块的「口径: …」里，既非强制指令、也无显式标记；用户可见性完全依赖模型是否转述。另有 `prompts.py:57` / `:126` 一条更宽的通用要求（「立春换年 / 早夜子时 / 真太阳时争议，说明不同流派口径，不单方面定论」）。**即：文档声明的是"必须主动提示用户"这一交互级保证，代码提供的是"在提示词里带上一句建议"——两者不等价。** 建议在文档中降级措辞，或把该 warning 升级为带标记的强制注入段。

**修复建议**：

1. 显式化意图，不再依赖库默认值：

   ```python
   ec.setSect(2 if sect == 2 else sect)   # 或直接 ec.setSect(sect)，配合下方常量
   ```
   并加注释说明 2 = 晚子时日柱沿用当日 + 时干次日五鼠遁，与 `00_知识库总索引.md:116` 对应。
2. 统一 `sect` 语义，收敛到**一处**常量化定义（如 `app/domain/sect.py` 定义 `SECT_EARLY=1` / `SECT_LATE=2` 及文案），让 `bazi.py`、`xianzhi_kline.py`、前端文案全部引用它，消除三处互相矛盾的 docstring。
3. 把"必须提示"从建议升级为机制：或在 `chart_builder` 的 warning 上加醒目标记并在 workflow 侧强制注入，或在 `24_标准分析流程.md` 的表述上降级为"应提示"。**两者必须对齐。**
4. 加一条金标准测试钉住 23:00–23:59 的四柱，使旗舰口径不可静默漂移。

1. **"deepagents 编译文件漏收 11 篇" —— 错。** 早期用「整文件字符串包含」判定，因标题层级与空白差异误判。改为按 H1 编号 + 多探针核对后确认：编译文件覆盖 **1–53 节，仅 `054_Trace链路追踪.md` 缺失**。

3. **各处行数 —— 早前数字偏小。** PowerShell `Measure-Object -Line` 与 `Get-Content` 会漏计空行（且对纯 LF 文件行为不同）。本报告全部行数改用「按 `\n` 计数」重测，例如 `README.md` 实为 555 行（非 431）、`docs/backend-architecture-review.md` 实为 949 行（非 577）。

第 3 点对本次范围的影响：`00_知识库总索引.md` 与 48 篇内容文档的行数均以重测值为准（合计 12,409 行）。
