# 2026-07-29 工作日志

## CloudBase 部署失败排查与修复

### 现象
镜像构建成功，但部署阶段报错：
`Liveness probe failed: dial tcp 10.22.22.144:80: connect: connection refused`
启动日志停在 `对话记忆存储: PostgreSQL` 后无进展。

### 根因
`main.py` 的 lifespan 启动事件里**同步连 PostgreSQL** 才放行 uvicorn 监听端口。
- `PostgresChatMemory.__init__` → `_ensure_schema()` → `ConnectionPool(open=True)` 在**启动时立即建连**；
- `knowledge_base.init()`（RAG 向量库）也同步连 PG。
容器与云数据库不在同一网络平面（连接串里 `172.17.0.9:5432` 疑似本地 Docker 网段，疑似非云 PG 真实地址），
连不上 → 启动事件卡死/抛错 → uvicorn 永不监听 80 → 探针被拒。

### 修复（已提交 59567c1）
- `app/config.py`：新增 `settings.pg_dsn(timeout=5)`，统一给 PG 连接串兜底加 `connect_timeout`，
  避免网络不通时连接长时间挂起。
- `app/memory/postgres_memory.py`：`ConnectionPool(open=False)` 懒连接；`_ensure_schema()` 的建连+建表包进
  try/except，数据库不可达时仅告警、`_schema_ready` 保持 False，不阻断启动（重启/首次使用时重试）。
- `app/rag/vector_store.py`：PGVector 改用 `settings.pg_dsn()`（带 connect_timeout）。
- `main.py`：把 `knowledge_base.init()`、`mcp_manager.start()`、暖启动缓存、`ensure_table()` 移入
  后台任务 `asyncio.create_task(_bg_init())`，启动事件先 `yield`（端口立即监听，探针通过），重活后台跑。
- `DEPLOY.md`：新增「第 8 节 容器访问数据库的网络连通性」，说明真正的修复是让容器能连上 PG（二选一）：
  1) 云托管服务放入数据库所在 VPC；2) 开启 PostgreSQL 外网地址并用 `*.rds.tencentdb.com`。

### 待用户操作（网络层，代码无法替代）
让容器真正连上数据库，二者其一：
- 云托管「服务设置 → 网络」选数据库所在 VPC/子网；或
- 云数据库 PostgreSQL 开启外网地址，把 `POSTGRES_CONNECTION_STRING` 改为 `*.rds.tencentdb.com:5432`（仍带 `?sslmode=require`）。
改完重新部署即可。

### 问题 2（代码 bug，已修，提交 6f3c979）
`main.py` 原 `port = int(os.environ.get("PORT", settings.app_port))`：CloudBase **不自动注入 PORT**，
于是读到 `APP_PORT=8123` → 容器监听 8123，探针连 80 → connection refused。
改为：容器内（`/.dockerenv` 或 `KUBERNETES_SERVICE_HOST` 存在）且无显式 `PORT` 时**强制监听 80**；
本地沿用 `APP_PORT`/`PORT`。Dockerfile 注释订正（去除"CloudBase 默认注入 PORT"的错误假设）。

### 澄清「内网要花钱」
CloudBase 关联私有网络（VPC）**本身免费**，仅 NAT 网关收费。仅关联 VPC、不开 NAT 不花钱。
→ 推荐用户在云托管「网络设置 → 私有网络」开启并选 Default-VPC / Default-Subnet（与 PG 同），即可内网直连 `172.17.0.9`，免费且最稳。
备选：用 PG 已开启的外网地址（容器公网访问已开，能通），但每次查询走公网、有流量费且密码明文走公网（靠 sslmode 加密）。

### 4 个 500 的根因
`users.py:126` 的 `_ensure_table()` 和 `user_data.py:29` 的 `_ensure_tables()`
都在 try/except **外部**调用 `_get_pool().connection()` + DDL。
任何异常（首次连接失败、DDL 执行错误等）直接冒泡 → FastAPI 默认处理 → 500。
受影响端点：`/api/ai/profiles`、`/api/ai/favorites`、`/api/ai/tarot_records`、`/api/ai/xianzhi/sessions/mine`。

### 修复（提交 cf22754）
- `users._ensure_table()`：整体包进 try/except，失败仅 warning + _TABLE_READY 保持 False
- `user_data._ensure_tables()`：拆为 `_ensure_tables()`(try/except 包装) + `_do_ensure_tables()`(原始 DDL)，避免 200+ 行重缩进

## 第五轮（23:02-23:05）：表已建好但仍 500，根因 PoolClosed

### 关键信息
- 云端 DB 表数量 **12** ✅（手动建表成功，含 users/message_store/session_metadata 等）
- 版本 **006 正常 100%** ✅（cf22754 已部署）
- 运行日志：`psycopg_pool.PoolClosed: the pool 'pool-1' is not open yet`

### 根因
第三轮修复时把 `ConnectionPool(open=True)` 改成了 `open=False`（防启动卡死），
但 `open=False` 意味着池子永远不建立连接 → 所有 `.connection()` 调用抛 `PoolClosed` → 500。
users.py / user_data.py 都共用 postgres_memory 的 `_get_pool()`，一处影响全局。

### 修复（提交 f75c752）
改回 `open=True`。安全是因为：
1. main.py lifespan 已把重活移到后台线程，启动不卡死
2. DSN 带 `connect_timeout=5`，网络不通最多等 5s
3. `_ensure_schema()` 有 try/except 保护
